In this section, we develop an executable model of a paid agent task in Lean.
We specify wallet authorization and settlement conditions, then compose payment
and task execution into a state transition system.

The accompanying Lean source is preserved from the [study snapshot at
`43f2620`](https://github.com/CloK-Lab/vdsi/tree/43f26201474a144b68924d2b485a0e3fd857c483).
It is separate from the current participant-node implementation.

The model combines the components introduced in [Modules and interactions](System/Note.mdx).
It uses native ETH accounting and models only the transfer value; gas fees
and network execution are omitted. It is a local composition model, not an x402
EVM payment implementation.

## Bind payment to a task

Agent A asks Agent B to echo `hello` for **0.003 ETH**. A starts with 0.01 ETH
and B with 0.002 ETH. A's wallet permits this amount and recipient. After the
modeled transfer, A has 0.007 ETH, B has 0.005 ETH, and B returns `hello`.

The requested service and input belong to the task. Payment terms bind the
whole request to an asset, amount, payer, recipient, and deadline:

```lean4 file="./Payment.lean" declaration="PaymentTerms"
```

The accounts use `eip155:1`, and `Ethereum.ether` identifies native ETH.
`Ethereum.milliEther 3` supplies the payment amount in wei. The account addresses
are local fixtures; this example sends no transaction.

`CanAuthorize` applies the [wallet policy](../../Native/Wallet/Note.mdx) and
requires the authenticated actor to be the task's caller. `authorize` records
approval without changing balances or producing a cryptographic signature.

## Transfer, then complete

The ledger records balances and used `(payer, nonce)` pairs. Settlement requires
enough funds, a fresh authorization, matching task and provider details, and
`now < expiresAt`. Time and nonces are local model values, not Ethereum
transaction fields.

An accepted settlement debits A, credits B, consumes the authorization, and
marks the task paid in one model transition. Other accounts and assets retain
their balances. The provider then returns the requested input.

```lean4 file="./Examples.lean" declaration="demo"
```

The local phases `requested`, `paid`, and `completed` describe this example's
ordering. They are separate from [A2A's task states](../../Reference/A2A/Note.mdx).
Recording a result also does not establish the quality of an arbitrary service;
the echo example computes its result directly from the input.

## Run

```sh
git clone --branch archive/pre-participant-model-20261010 https://github.com/CloK-Lab/vdsi.git vdsi-studies
cd vdsi-studies
lake build
lake exe demo
```

The system trace records one execution of this example. The table displays ETH;
`lake exe demo` prints the same balances as integers in wei.

| State | Approval pending | A's ETH | B's ETH | Task |
| --- | --- | --- | --- | --- |
| Request | No | 0.010 | 0.002 | Requested |
| Authorize | Yes | 0.010 | 0.002 | Requested |
| Settle | No | 0.007 | 0.005 | Paid |
| Execute | No | 0.007 | 0.005 | Completed: `hello` |

The final balances are **7,000,000,000,000,000 wei** for A and
**5,000,000,000,000,000 wei** for B. The result is `completed "hello"`.
A separate test-network balance of 7 base units is unchanged.

The build checks rejection of excessive spending, wrong actors, recipients or
networks, expired authorizations, insufficient funds, changed tasks, replayed
payments, and execution before payment.

Payment and service success are separate: if the service fails after settlement,
the preceding paid state still represents the completed transfer. `trace`
returning `none` reports a rejected sequence; it does not reverse earlier state
transitions.
